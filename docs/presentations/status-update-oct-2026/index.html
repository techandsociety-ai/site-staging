Every deploy is tested first

In July: The test suite didn’t run, and deploys went out unchecked.

Now: CI runs 2,382 checks before anything deploys, including checks against published CHIP50 reports, and posts the results of every run on the test-status page.

Next: Fix the 13 known problems the tests still flag, and check the live servers after each deploy, not just the code before it.

Rebuilding the data

In July: Import depended on a manual CSV export from someone on the team, labels and wording were typed into the code by hand, and 11 of the 47 waves weren’t in the database at all.

Now: All 47 raw wave files sit in one bucket, and a new loader rebuilt every wave in a sandbox, labeled from the survey’s own codebook. We planned the replacement pipeline with Hong and Katya, and fixed the data bugs Lazer and others found, from wrong labels and wording to the wrong weight on political and state questions.

Next: Load Katya’s cleaned data through the new pipeline as it rolls in, through the end of the year, and move production onto it.

specialized servers, a paid tier

One codebase, as many servers as we need

In July: The AI survey ran on a separate fork of the code.

Now: Each server is a profile with its own data, roster and address: today the full panel, the Wave 38.6 AI survey and sentinel. A new server is a profile, not a fork.

Next: Specialized servers for particular topics or partners, a paid tier, and more, each one a new profile.

Ask from a browser

In July: The old chat ran in a cloud project we couldn’t administer, and everyone used one shared Google account.

Now: chat.techandsociety.ai runs on the project’s own cloud account, and people on the roster sign in as themselves to ask the AI survey questions, no Claude setup needed.

Next: Add the full panel alongside the AI survey, and give each person a spending allowance that fits real use.

Survey expertise

In July: The tools returned bare numbers, and the model had to guess what they meant.

Now: The server tells the model how to read the data, which heads off mistakes we saw models make: averaging “Not sure” into a scale, borrowing a same-named question from another wave, reading a suppressed cell as zero.

Next: There’s a lot more to do, and it’s what could make the MCP great: a tool that teaches people how to read a survey, not one that just hands them numbers.

Ready for early access

In July: Any Google account could get in, nothing recorded who ran what, and how it all ran lived in two people’s heads.

Now: Each server has its own roster that admins edit without a redeploy, and every tool call is logged with who made it. A maintenance guide with runbooks lets someone new run it, alerts email when a scheduled job fails, and retiring the old addresses cut Cloud Run costs.

Next: A staging server, so changes are tried before users see them, and a usage history that outlasts the 30 days the logs keep now.

The roadmap I’d recommend

First, starting now

Split server.py

Break the 10,200-line file into modules, about 20 hours with careful review. Nothing waits on it, and it’s the biggest obstacle to anyone else working on the code.

Right after

One query path

Send every table tool through one path for queries, suppression and labels, so a fix lands everywhere at once instead of tool by tool.

Now through year’s end

Move production to the new pipeline

Katya’s cleaned data is rolling in now and should be complete by the end of the year. We can load it through the new pipeline as it arrives, then move production onto it, so every number traces back to the raw survey files.

Throughout

More survey expertise

Build in what users and reports get wrong. It takes the least engineering and could matter most.
